# Pipeline

An interactive native Herdr prototype. Visitor mode: Operate. The user observes a project-level planning agent dispatching tasks into a limited number of parallel work slots. A project may contain multiple repositories; a task may coordinate changes across several of them.

The approved direction is a stable constellation with left-to-right flow: picked tasks and watched columns feed a queue; a central planner chooses work; workers produce related PRs; approvals release coordinated merges. Both task intake methods share one queue. Quota reserve, dependency completion and outstanding PR limits govern dispatch. Review releases a worker slot. Doing, Review and Done correspond to successful launch, verified output and completed integration.

The simulation uses labeled synthetic tasks and a deterministic model of planning, execution, checks, quota and PRs; it does not start agents, modify task services or change Git repositories. Live mode (below) runs real agents. The eventual planner will be an agent, with constraints enforced by the execution engine. Background execution after quitting Herdr is outside the initial scope. Closing the view keeps the prototype progressing through a tracker in the tab bar; state is saved and resumes without catching up elapsed time while Herdr was closed.

## Direction contract

THESIS: Make dispatch visible and explain every wait. Task nodes travel through a planner into fixed work slots, then review and merge.

OWN-WORLD: Inherit Herdr's theme colors, native controls, typography and focus behavior. Use precise paths, small round ports, quiet orbital geometry and spacious labels. Color indicates state; text always names it.

STORY: Pick example tasks or watch a column, start the pipeline, observe why the planner chooses independent work, inspect a multi-repository task and approve its related PRs.

FIRST VIEWPORT: Pipeline title and Simulation badge above compact controls; a large spatial canvas owns the view. Queue at left, planner near one-third, three work slots beyond it, review at right and a completed trail below. A narrow inspector opens on selection. Native position transitions carry the dispatch moment. Reduced motion replaces travel with immediate state changes.

FORM: User-selected constellation, confirmed in conversation. Code-led native data geometry; no concept roll or raster comp substitutes for the pinned interaction. The ordinary mod system remains the visual authority.

FINISH: unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, DESIGN.md, and every shipping raster carrying its provenance

## Live execution (first version)

Live mode runs real agents on the project's repository. Tasks are typed in Pipeline or come from a tracker: the Plane project linked to the repository, or Linear filtered by scope (mine, unassigned, all), an optional team and an optional project. The Linear drawer has a searchable Choose team picker; its selection is saved per pipeline, filters issues on Linear before they are returned, limits the project picker to that team, and clears an existing project when the team changes. A selected team supplies its workflow states even when no tickets match. Tickets are picked from open ones, or queued automatically from a watched state, each ticket claimed once. Both are read through the panels' local readers (`herdr-plane`, `herdr-linear`, via `mods/pipeline/ticket-source.js`), which run on this computer even for a project on another machine. A task keeps the ticket as `task.ticket` (`provider`, `uuid`, `key`, `url`, `status`, and for Linear `team`); watches and their last error live per provider in `watching` and `sourceErrors`. Linear states are matched by name (list_issues takes a state name), a Linear watch keeps the filter it was made with and needs My tickets, a team or a project, and tickets are read in full with `get_issue` before they are queued (up to 10 at a time), because Linear's list shortens descriptions to 500 characters. Tasks wait for each other through `task.depends` (task ids picked in the inspector, refused when they would close a circle) and `task.blockers` (a ticket's blocked-by links, `{key, uuid, title, url, closed}`, read with the ticket: Linear's `get_issue` relations, then each blocker's status; Plane's `work-items/<id>/relations/` `blocked_by`, then each work item). `waitsFor` resolves a blocker to a task with the same ticket key when there is one, which must merge; otherwise its ticket must be closed, and the runner re-reads blockers once a minute for queued tasks that wait on outside tickets. `unblock` (Start anyway) skips both; removing or discarding a task drops it from others' `depends`. With PR delivery, a task with dependencies starts from `origin/<branch>` fetched at launch (`worktrees.py inspect` with `remote`), because its blocker merged on GitHub rather than in the project folder. Each dispatched task gets an isolated worktree and branch (`pipeline/<task>-<run>`, made by the shared `mods/linear/worktrees.py` helper) and an agent tab in the space Start was pressed in. The chosen agent starts with its plain `run` command plus, for Claude Code and Codex, the model and effort saved per agent in `tuning` (`--model`/`--effort`, or `-m`/`-c model_reasoning_effort=`); unset values leave the agent's own default. Codex's model buttons and effort levels come from its `models_cache.json` (`$CODEX_HOME`, else `~/.codex`) on the project's machine, hidden models left out; picking a model that lacks the saved effort resets the effort. Herdr's agent status drives the card: working, blocked (Needs you), done or idle after working (Ready for review). Agents that report no status yet are checked for their folder-trust prompt. With a check command set, a finished task first runs it in its worktree (`sh -c`, up to 10 minutes, beside the Git queue): a pass moves it to review, a failure goes back to the agent with the end of the output up to twice, then waits for the person. A finished turn only counts after the agent was seen working, so a stale status never ends the next turn early. Approving a task runs `mods/pipeline/delivery.py`: commit leftovers, rebase onto the project folder's current branch, fast-forward, then close the agent's tab and remove the worktree and branch. With pull request delivery, approving instead pushes the branch to `origin` and opens a PR with `gh pr create` into the worktree's start branch (`delivery.py publish`, which reuses an existing PR). `merging` covers only the push and `gh pr create`; an open PR is its own `pr` status, which the runner asks `gh pr view` about once a minute, finishing the task on MERGED or returning it to review on CLOSED. While it is OPEN, `delivery.py pr_state` also reads draft, mergeable, mergeStateStatus, reviewDecision and statusCheckRollup, summarised into `task.pr.status` (`draft`, `mergeable`, `mergeState`, `review`, `failed`, `failing` names, `pending`, `passed`) by `prStatus`, which leaves the store alone when nothing changed. `prNeeds` picks the card line (draft, conflicts, failing checks, changes requested, running checks, review required, behind, blocked, ready) and `prChecklist` the inspector rows. Open PRs have their own section below the review cards in `layoutScene`, which shares the review column's rows between the two. With `autoPr` set, a task that reaches review on its own (agent done with no check, or checks passed) is approved immediately; failing checks, Review anyway and a closed PR still wait for the person. The runner (`mods/pipeline/pipeline-live.js`) lives in the tab-bar tracker, runs one Git job at a time and never replays a start it could not confirm.

### Several repositories

`state.repositories` (`[{name, path}]`, saved since version 5) lists where Live tasks may work: the project folder first (`name` is `state.repo`, `path` the context's `cwd`), then repositories added in Settings. The view checks a typed path on `context.on` with `git rev-parse --show-toplevel` (through `sh`, from the project folder, `~` expanded there), refuses a toplevel already listed or equal to the project's, and `addRepository` stores the toplevel under its folder name, made unique with `-2`, `-3`. `removeRepository` never removes the first and drops the name from queued tasks without worktrees (falling back to the project); started work keeps the `source` path recorded on its worktrees. `task.repos` holds repository names, in Settings order; the `repos` action (shared with the simulation) toggles them on a queued task without worktrees, keeping at least one. New tasks start with `[state.repo]`, and the planner never chooses repositories.

A task's worktrees are `task.workspaces` and `task.planned`, both keyed by repository name: `{root, cwd, branch, base, target, source, run}`. The launch inspects and creates each missing one from its `source` (`worktrees.py` with the context's `cwd` set to it), passing the first one's `runId` to the others so every branch has the same name, and the `remote` fetch to each when it applies. A launch that stopped part way reuses the worktrees it made. `workspacesOf(task)` lists them in `task.repos` order: the agent starts in the first, `agentRun` adds `--add-dir=<root>` per other one for Claude Code and Codex (`AGENT_OPTIONS[key].dirs`, the `=` form so Claude's variadic option can't take the next argument), and `prompt` lists every worktree with its branch, start branch and commit for any agent. The check runs in each worktree in turn; `checkFailed` carries the failing names (`task.checkRepos`), and the output heads each repository's tail with its name.

Local delivery is one `delivery.py merge` call with `repos: [{name, root, worktree, branch, base}]`: `prepare` checks every repository (detached HEAD, missing branch, uncommitted changes) and commits leftovers, then every changed branch is rebased, and only then fast-forwarded (`land`). An unchanged repository is skipped; none changed is an error. A fast-forward that fails after others landed returns `merged` and `failed` instead of raising, and the runner keeps the task in review naming both; landed repositories count as `already` merged next time. Errors from a task across repositories are prefixed with the repository name. The reducer gives a live task one approval for all its repositories (`approvals` set to `task.repos`), and the merge queue at the end of `reduce`, which the simulation already used, moves an approved task to `merging` only when no other merging task holds one of its repositories. `mergeFailed`, `prClosed`, `recheck` and the agent working again clear the approval.

With pull requests, `publish` runs per changed repository (`optional` skips an unchanged one in a task across several), skipping repositories whose PR already merged; when more than one is open, `delivery.py pr_edit` rewrites each body with the others' links (a failed edit is ignored). `task.prs` is keyed by repository: `{url, number, status, merged}`. The runner asks about each unmerged PR once a minute; `prStatus` and `prClosed` carry `repo`, and `prMerged` marks one merged and finishes the task when all are. A closed PR drops from `task.prs` and returns the task to review; the others stay open and approving again reuses them. `prNeed(pr, target)` ranks one PR's need, `prNeeds(task)` shows the most pressing across open PRs (prefixed with the repository when the task has several), and `prChecklist(pr, target)` lists one PR's rows. A ticket's `link` update stays one per task: with several PRs it carries `links`, and `updateTicket` adds each. Discard and cleanup remove every worktree in `workspaces` and `planned`, trying all before reporting the first failure. `outstandingCount` counts repositories, so the review limit does too.

`migrate` turns a version 4 live save's `workspace`, `planned` and `pr` into the keyed fields under the task's first repository and adds `repositories`.

### Ticket updates

Pipeline writes to a tracker only when `ticketUpdates[provider]` (`start` and `merge`, each a `{id, name}` state or null, and `link`) says so; all are off by default. The reducer queues an update on the ticket at `launched` (`start`, skipped when `ticket.moved` already has it, so a retried task doesn't move its ticket again), `prOpened` (`link`, titled `PR #N: <task title>`) and `merged` (`merge`, for a local merge or a PR merged on GitHub). Each sits in `ticket.pending` with a serial `n`; the runner's `updateTickets` makes the first one per task beside the Git queue (`host.updateTicket`, `ticket-source.js` `updateTicket`) and reports it with `ticketUpdated`, which drops the update, records `ticket.update` (`kind`, `ok`, `error`, `errorKind`, `at`, `text`), adds an event, and on success adds the kind to `ticket.moved` and the state name to `ticket.status`. A failure goes to `ticket.failed` and stays there until `ticketRetry` (Try again) queues it again; nothing retries by itself, and no update changes the task's status. Settings lists states with the trackers' `states` ops: the linked Plane project's, and Linear's for the teams of queued tickets (and of the open drawer's list), merged by name, which `save_issue` accepts. A ticket leaving a watched state this way is not queued again, because `claimed` remembers it.

Both writes read the ticket first and do nothing when it already has the state or the link. Plane: `update_state` GETs `work-items/<id>/` and PATCHes `{state}`; `add_link` lists `work-items/<id>/links/` and POSTs `{url, title}` if the URL is missing. Plane's `call` reports a write it could not confirm as `uncertain`, and nothing follows it. Linear: `update_state` reads `get_issue` `status` and calls `save_issue {id, state}`; `add_link` reads `get_issue` `attachments` and calls `save_issue {id, links: [{url, title}]}`. `herdr-linear` allows exactly those two `save_issue` argument sets (`WRITES`) besides its read tools. A 403 or a tool error about permission or scope on a write, or a Claude login only for the read-only MCP endpoint, is `write_access` ("Pipeline needs write access to Linear…"), and the inspector offers the API key connect flow; a 5xx or lost connection on a write is `uncertain`. Agents are still told not to change a ticket's status or assignee.

### Review, order and notices

The review inspector lists a task's changed files per worktree (`changedFiles` in `pipeline-live.js`, from `git diff <base> --name-status` and `--numstat` plus untracked files from `git status`, all with `-z`; `base` is the worktree's start commit, or, once the task's branch was rebased onto its target, the newer commit it now shares with it (`FORK` in `main.js`), so other tasks' merges never show up as this task's work). A file opens the `changes-modal` dialog with `props.base`, which makes its viewer diff against that commit instead of `HEAD`; nothing else in that clone changes. The list is read once per task status (`peekAt`), and again on demand.

The queue starts, and is drawn, in `queueOrder`: `task.rank` (set by `first`, the highest last-marked, cleared when the task starts), then priority, then id. `task.tune` (`{model, effort}`, set by `tuneTask` on a queued task) overrides the agent's `tuning` per field through `taskTuning`, which `agentRun` and the launch's tuning label use.

Live tasks count the time their agent works or their checks run: `reduce` stamps `task.at` whenever a live task changes status and, when it leaves `working` or `testing`, adds the time since to `task.spent`. `timing` turns that into the card's elapsed time and the completed row's duration, so time waiting for an answer, a review or a merge never counts. Tasks saved before this have neither and show nothing.

`liveNotices(before, after)` lists what a change should announce: checks failed, stopped, a trust prompt, a refused merge or pull request, a closed or merged pull request, a pull request whose need turns ready or blocked, checked work ready for review, and an automatic merge. An agent that asks or finishes is left to Herdr's own notification. `LiveRunner.apply` hands each to `host.announce`, which posts it unless a Pipeline pane has focus; `state.quiet` (`quiet` action, Notify me) silences them. A merge refused for a conflict offers `rebaseRequest` to the agent (`resolve` in the view, then `resolving`, which clears the refusal); the agent working again moves the card as any feedback does.

The runner reads a working task's screen once a minute (`watchStall`, after the agent was seen working); ten minutes (`STALL`) without a change (compared by `screenText`, which drops digits and symbols, since agents tick a timer, token count and spinner while they wait) sets `task.stalled` to when the screen last changed (`stalled` action), which the card, the inspector and a notice show, and a changed screen or any other status clears it. `countUsage` asks `usage.py` for the first worktree's tokens once per finished turn (status `input`, `testing`, `review`, `failed` or `pr`, again after the agent worked): it sums each reply's `usage` once across Claude Code's transcripts in `~/.claude/projects/<folder>` (`CLAUDE_CONFIG_DIR` respected), plus the last `total_token_usage` of each Codex session in `~/.codex/sessions` (`CODEX_HOME` respected) whose `session_meta` cwd is the worktree or inside it (input less cached is read, `cached_input_tokens` cached, `output_tokens` written, each changed total a turn), into `task.usage` (`{written, read, cached, turns}`). Other agents have no usage. `event` also appends a live task's lines to `task.log` (30 kept), which `taskLog` prefers over the shared 40-line log.

In Live the scene's centre is a button (`pipeline-sun`) naming the most pressing need (questions, stopped tasks, reviews) and opening it; the simulation keeps the Planner label. The inspector fades in over 160 ms.

Task cards are 164 wide below 1320 px of window width, 188 up to 1500 and 212 beyond (`cardWidth`, from the window rather than the scene, so opening the inspector never resizes them).

### Planner agent

`state.planner` (`{on, agent, model, effort}`, `plannerSetup`) turns on planning. `plannerAgent` is `claude` or `codex`: the one picked, else the task agent when it is Codex, else Claude Code; picking another drops the model and effort. `planSig(task)` covers what the planner reads about a queued task (title, details, repositories, priority, waits you set, and each ticket blocker's key and whether it is closed); `planned(state)` is true while every queued task has a `task.plan` with the current signature, so tasks leaving the queue never ask again. While it isn't, `plannerHolds` stops dispatch, unless the last plan failed for the same tasks (`failedFor`), so a failing planner never blocks the pipeline. The runner (`LiveRunner.plan`) waits until `planKey` (queued ids and signatures) has been the same for four seconds, sends `planning`, and calls `host.plan` with `planArgs`, which returns `{agent, args, schema, prompt, tuning}`. `mods/pipeline/planner.py` runs it and streams the agent's events: Codex as `codex exec --json --output-schema <file> -o <file> --sandbox read-only --ephemeral --skip-git-repo-check` with `-m`/`-c model_reasoning_effort` and `--add-dir` (its last message is the plan), Claude Code as `claude -p --output-format stream-json --verbose --json-schema` with `--tools Read,Grep,Glob`, `--add-dir` for the other repositories, `--strict-mcp-config`, `--disable-slash-commands`, `--no-session-persistence`, `--json-schema PLAN_SCHEMA` and `planPrompt(state)` (which lists each ticket's blockers as in the pipeline with their task, closed, or still open outside it, and says Pipeline already enforces them), in the project folder, for up to five minutes. `planner.py` turns the events into a trace ("Reads src/math.js", "Searches for …", "Runs rg …", "Thinks: …") and returns `{plan, error, trace, ms, cost, tokens}`; `readPlan` takes that, throwing with the trace when there is no plan, (`summary`, `order`, `tasks[{id, waits, reason}]`). `planned` applies it only when the queue is still the one asked about: `task.plan = {n, reason, waits, sig}`, unknown ids dropped, missing ones appended in the usual order, and a wait kept only when it points at a started task or one the plan starts earlier, and `canWaitFor` allows it. `startOrder` puts `rank` (Start first) before `plan.n`, and `waitsFor` adds the plan's waits (`planner: true`) unless the task was unblocked. `planning` keeps the prompt, agent, model and effort; `planned` and `planFailed` add the trace, time, tokens and cost, and `planned` keeps `planning.tasks` (each queued task's title, reason and waits, in order) so the Planner drawer (`plannerView`) shows the plan after its tasks start. `watchPlan` marks the next plan to be watched: `planning` takes the mark, and the tracker runs `planner.py` with `watch` in a terminal tab named Planner (in the pipeline's space), which prints the prompt and each step, writes its result to a folder under `/tmp`, and the tracker waits for that file. A restart turns a running plan into a failure. `replan` drops the plans of queued tasks. Pressing Start in Live now says "Started. Agents start for queued tasks…", so it isn't mistaken for the planner agent.
